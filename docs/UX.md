## ۱. تجربهٔ کاربری فقط ظاهر نیست (نورمن/نیلسن + گرت)

UX یعنی کل تعامل کاربر با شرکت، خدمات و محصول؛ UI فقط بخشی از آن است. اگر رابط عالی باشد ولی موجودی یا قیمت‌ها قدیمی باشد، تجربه بد است.
پنج لایهٔ گرت، با پاسخ فعلی این پروژه:

| لایه | سؤال | پاسخ فعلی |
| --- | --- | --- |
| راهبرد | چرا و برای کی؟ | بازار B2B موبایل/ساعت/اسپیکر کارکرده برای همکاران؛ شروع از تبریز |
| دامنه | چه قابلیت‌هایی؟ | لیست قیمت، خرید، ثبت دستگاه، دستگاه‌های من، تنظیمات |
| ساختار | چطور سازمان‌دهی شود؟ | خانه (لیست قیمت) · ثبت دستگاه · سبد · پنل (دستگاه‌های من، تنظیمات، دربارهٔ ما) |
| اسکلت | چیدمان و ناوبری | نوار پایین (موبایل)، منوی بالا (دسکتاپ)، فیلتر کناری/برگه |
| ظاهر | حس و نمای حسی | تیره/نارنجی، فونت وزیر، آیکن‌های یکدست |

**قاعده:** مشکل هر لایه را در همان لایه حل کن. مثلاً «همکار نمی‌داند چرا قیمت نمی‌بیند» مشکل ساختار/محتواست، نه رنگ.

## ۳. قواعد بصری (Refactoring UI + NN/g دربارهٔ Flat UI)

- **سلسله‌مراتب با رنگ و وزن، نه فقط اندازه.** متن مهم: پررنگ‌تر. ثانویه: خاکستری‌تر. حداقل کنتراست ۴.۵:۱.
- **روی پس‌زمینهٔ رنگی خاکستری نگذار.** روی تیره از سفید با شفافیت یا رنگ هم‌خانواده استفاده کن (صفحهٔ «دربارهٔ ما» همین‌طور است).
- **سایه با آفست عمودی**، نه هالهٔ صفر-آفست.
- **کمتر کادر.** برای جدا کردن از فاصله یا رنگ پس‌زمینهٔ متفاوت استفاده کن.
- **آیکن‌های کوچک را بزرگ نکن.**
- **یک دکمهٔ اصلی در هر صفحه.** اصلی: پر و پررنگ. ثانویه: خطی. سوم: شبیه لینک.
  اقدام مخرب (حذف) تا وقتی اقدام اصلی صفحه نیست، سطح سوم است. ردیف‌های لیست قیمت «خرید» را خطی دارند؛ نارنجی فقط برای اقدام اصلی صفحه است.
- **قابلیت کلیک باید دیده شود** (NN/g: نشانه‌های ضعیف، ۲۲٪ زمان بیشتر و ۲۵٪ نگاه بیشتر). نام دستگاه در لیست زیرخط دارد، لینک‌ها رنگ متمایز دارند، چیپ‌ها حالت انتخاب‌شده دارند.
  تخت بودن فقط وقتی مجاز است که تراکم اطلاعات کم، چیدمان استاندارد و هدف پررنگ باشد؛ لیست قیمت هیچ‌کدام را ندارد.

## ۴. ساختار کد: Atomic Design در برابر FSD

Atomic Design (اتم → مولکول → ارگانیسم → قالب → صفحه) برای ساخت سیستم طراحی است؛ پروژه از FSD (shared → entities → features → widgets → pages) استفاده می‌کند و ربطشان این است:

| Atomic | در این پروژه |
| --- | --- |
| اتم | `shared/ui` (دکمه، فیلد، چیپ، تب) و توکن‌ها در `tokens.css` |
| مولکول | کامپوننت‌های کوچک `features/*/ui` (ChipGroup، PanelMenu) |
| ارگانیسم | `widgets/*` (نوار پایین، سر صفحه، کارت کاتالوگ) |
| صفحه | `pages/*` |

**قاعده:** اتم جدید فقط وقتی به `shared` برود که در دو جا لازم شد؛ تا آن موقع در همان اسلایس بماند. `npm run check:arch` وابستگی‌ها را نگه می‌دارد.

## ۵. برنامهٔ تست با کاربر (NN/g: ۵ کاربر + چیت‌شیت تحقیق)

اصل: هیچ تست یعنی هیچ بینش؛ پنج کاربر ۸۵٪ مشکلات را نشان می‌دهند. بهتر است به‌جای یک تست بزرگ، چند تست کوچک و تکراری انجام شود:
تست ← اصلاح ← تست دوباره.

دو گروه کاربر داریم (خریدار و فروشنده)، پس ۳–۴ نفر از هر گروه در هر دور.

**دور ۱ (قبل از انتشار گسترده):** ۳–۴ خریدار + ۳–۴ فروشندهٔ واقعی در تبریز، با موبایل خودشان، با روش «با صدای بلند فکر کن». بدون راهنمایی، فقط مشاهده.

وظایف خریدار:
1. «آیفون ۱۷ پرو مکس ۲۵۶ با کد کشور CH پیدا کن و قیمتش را بگو.»
2. «دو دستگاه را در سبد بگذار و خریدت را ثبت کن.»
3. «بفهم گرید «تمیز» یعنی چه.»

وظایف فروشنده:
1. «گوشی‌ات را برای فروش ثبت کن.» (تا آخر فرم عکس‌ها)
2. «آگهی‌ای را که ثبت کردی پیدا کن و حذف کن، بعد برش گردان.»
3. «شهر آگهی‌ها را تغییر بده.»

**چه چیزی اندازه بگیریم:** انجام شد یا نه، زمان، تعداد اشتباه کلیک، جمله‌هایی که کاربر دربارهٔ واژه‌ها می‌گوید («درحد» را فهمید؟).
**بعد از هر دور:** ۱۰ مشکل اول را مرتب کن، اصلاح کن، دور بعد با افراد جدید.
**اگر فقط یک کار می‌توانی بکنی:** همین تست با فکر کردن با صدای بلند.

### شنیدن (بعد از انتشار)
- پرسش‌هایی که به واتساپ/تلگرام پشتیبانی می‌رسد را ماهی یک بار فهرست کن؛ هر سؤال تکراری یک مشکل طراحی است (قاعدهٔ ۱۰).
- جستجوهای بی‌نتیجهٔ لیست قیمت (مدل‌هایی که همکاران می‌خواهند و نداریم).
- شاخص‌ها: نرخ تکمیل ثبت دستگاه، نرخ تکمیل خرید، زمان تا اولین قیمت دیده‌شده.
